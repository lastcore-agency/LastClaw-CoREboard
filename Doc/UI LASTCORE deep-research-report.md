# รายงานออกแบบเว็บสามส่วนสำหรับ OpenClaw Command Center บนมือถือ

## บทสรุปสำหรับตัดสินใจ

จากชุดอ้างอิงใน entity["company","GitHub","code hosting platform"] และวิดีโอใน entity["company","YouTube","video platform"] แนวทางที่เร็วที่สุดไม่ใช่ทำ “เว็บ 3 ตัว = 3 โปรเจกต์แยก” แต่ทำ **1 codebase ที่มี 3 surface หลัก** แล้วเสิร์ฟเป็น custom Control UI ของ OpenClaw ผ่าน `gateway.controlUi.root` เพื่อให้หน้าเว็บคุยกับ Gateway เดิมผ่าน WebSocket control plane เดียวกันได้ทันที โดย OpenClaw รองรับการชี้ Control UI ไปที่ static build ของคุณอยู่แล้ว และ Gateway WS เปิด method families สำหรับ status, channels, models, chat, agents, sessions, config, skills, tools, cron รวมถึง event stream หลักไว้อย่างเป็นทางการแล้ว. citeturn18view7turn26view0turn18view2

ถ้าจะเอา “เรียบง่าย ใช้ได้จริง เสร็จเร็ว” ให้ใช้ **Vite + React + TypeScript + Tailwind + Zustand** เป็นแกน เพราะทั้ง OpenClaw Office และ openclaw-desktop ใช้แนวนี้ในงานที่มี chat, settings, skills, plugins, analytics, และ responsive UI อยู่แล้ว ขณะที่ OpenClaw-bot-review แสดงให้เห็นอีกทางว่าถ้าต้องการ dashboard ที่เบาที่สุด ก็สามารถยืนบน config/session data เดิมของ OpenClaw ได้โดยไม่ต้องเพิ่มฐานข้อมูล. citeturn5view5turn4view6turn3view4

คำตัดสินที่ชัดที่สุดมี 2 ข้อ ข้อแรกคือ **เว็บทั้งสามควรอยู่ในแอปเดียว** และใช้ bottom navigation บนมือถือเป็น “Center / Studio / Board” ไม่ใช่แยก domain หรือแยก stack เพราะทุกอย่างอาศัย data plane เดียวกันจาก Gateway อยู่แล้ว. ข้อสองคือ **ฟีเจอร์ Telegram ต้องทำแบบ bridge/mirror ผ่าน Gateway session** ไม่ใช่พยายามฝัง Telegram เต็มตัวลงในเว็บ เพราะเส้นทางนั้นจะทำให้ช้าและเปราะเกินจำเป็น. citeturn26view0turn17view5

## สิ่งที่ชุดอ้างอิงบอกชัด

วิดีโอที่ให้มาบน YouTube ใช้ชื่อว่า *How To Build Your Own OpenClaw MISSION CONTROL Dashboard* และเมื่อจับคู่กับ repo mission-control จะเห็นภาพชัดว่า reference ชุดนี้แข็งแรงมากในเรื่อง **orchestration และ task board** ไม่ใช่เรื่อง mobile command center แบบเบา ๆ mission-control เองขยายไปไกลถึง research → ideation → swipe → build → test → review → PR, ใช้ SQLite, มี Convoy Mode, cost tracking, health monitoring, checkpoint recovery และ operator chat ซึ่งดีมากถ้าจะทำระบบ “สั่งงานทีม agent แบบ product engine” แต่ใหญ่เกินโจทย์ “เว็บมือถือที่ควบคุมง่าย เสร็จเร็ว”. citeturn11search0turn6view1turn7view1

แหล่งอ้างอิงที่ตรงโจทย์ที่สุดคือ **OpenClaw Office** เพราะมันมีครบทั้ง virtual office, chat workspace, control console, pages สำหรับ Dashboard, Agents, Channels, Skills, Cron และ Settings และยังระบุชัดว่ามี mobile optimization พร้อม auto-switch ไปโหมด 2D บนมือถือด้วย อีกทั้งยังใช้ Vite, React, Tailwind, Zustand, Recharts, i18next และเชื่อมกับ OpenClaw Gateway ผ่าน WebSocket ตรง ๆ ซึ่งเท่ากับว่ามันให้ “information architecture ที่ใกล้เคียงโจทย์ที่สุด” อยู่แล้ว. สิ่งที่ควรยืมคือโครงหน้าและโครงข้อมูล ไม่ใช่จำเป็นต้องยก isometric office มาทั้งหมด. citeturn5view5turn3view1turn3view2

แหล่งอ้างอิงลำดับถัดมาคือ **openclaw-desktop** และ **OpenClaw-bot-review** ฝั่ง openclaw-desktop เด่นมากเรื่อง Config Manager แบบ smart merge, plugin system แบบ modular, Skills Marketplace จาก ClawHub, Agent Hub, Tools/MCP Tools, Dashboard และ model picker; repo ยังระบุ plugin grid แบบ responsive 3/2/1 คอลัมน์ตาม desktop/tablet/mobile ซึ่งเป็นแนวคิด UI ที่นำมาแปลงเป็นมือถือได้ดีมาก ส่วน OpenClaw-bot-review โดดเด่นด้าน “status dashboard ที่เบาและเร็ว” เพราะอ่าน `~/.openclaw/openclaw.json` และ local session files ตรง ๆ, ไม่ใช้ฐานข้อมูล, มี gateway health, model list, session management, stats, auto refresh และ pixel office เป็นของแถม. สอง repo นี้รวมกันคือแม่แบบที่ดีมากสำหรับ “Studio + Board”. citeturn15view2turn15view3turn15view5turn5view0

ส่วน **LobsterBoard** มีคุณค่าในฐานะแม่แบบของ “dashboard layer” มากกว่าการเป็นแกนของทั้งระบบ เพราะมันเป็น self-hosted drag-and-drop dashboard builder แบบไม่มี cloud dependency, มี 60+ widgets, live data ผ่าน SSE, template gallery และรองรับ multi-server monitoring ได้ แต่ตัวรูปแบบ editor ของมันเหมาะกับจอใหญ่หรือโหมด ops/kiosk มากกว่าหน้า command center มือถือ. ถ้าคุณจะมี board ปรับได้เองในภายหลัง LobsterBoard คือ reference ที่ดีมาก แต่ไม่ควรเอามาเป็นหน้าหลักของ v1. citeturn5view3turn4view7

รีโปอย่าง **Claw-Empire**, **Star Office UI** และ **ClawWork** มีประโยชน์เชิงแรงบันดาลใจ แต่ไม่ใช่ฐานเริ่มทำถ้าต้องการเสร็จเร็วจริง Claw-Empire เป็น local-first virtual company simulator ที่มี worktrees, office packs, provider orchestration และ deployment complexity สูง; Star Office UI เน้น pixel-art office, room design, daily notes, desktop pet mode แม้จะรองรับมือถือ; ClawWork เน้น economic benchmark และ “AI coworker” ด้านรายได้/ต้นทุนจาก GDPVal tasks. ทั้งสามตัวนี้พิสูจน์ว่า ecosystem มีของเล่นเยอะมาก แต่ถ้าดึงเข้ามาในรอบแรกจะทำให้ scope บวมทันที. citeturn14view0turn14view1turn3view7turn2search4turn13view0

## สิ่งที่ไม่ควรทำในเวอร์ชันแรก

- **ไม่ควรพยายามฝังหน้าต่าง group chat ของ entity["company","Telegram","messaging platform"] แบบ “Telegram เต็มตัวในเว็บ”** เพราะ Telegram widgets อย่างเป็นทางการมีแค่ sharing button, post widget, login widget และ discussion widget โดย post widget ใช้สำหรับ embed ข้อความจาก public groups/channels และ Mini Apps เป็นโมเดล “เปิดเว็บของคุณใน Telegram” ไม่ใช่ “เปิด Telegram ทั้งตัวในเว็บของคุณ”. ทางที่ใช้งานได้จริงคือ mirror chat ผ่าน Gateway session แทน. citeturn29view0turn29view1turn29view2

- **ไม่ควรเริ่มจาก visual office/pixel office เต็มระบบ** แม้ repo หลายตัวพิสูจน์ว่าทำได้ เพราะแม้แต่ OpenClaw Office เองยังเลือก auto-switch ไป 2D บนมือถือ และ Star Office UI ก็ชูเรื่อง mobile adaptation ว่า “มือถือเปิดดูได้” แปลว่าบนจอเล็ก ความสำเร็จมาจากการลด complexity ไม่ใช่เพิ่ม scene. v1 ควรเป็น card/list/sheet UI ก่อน แล้วค่อยใส่ office skin ในรอบหลัง. citeturn5view5turn2search4turn3view7turn22search0

- **ไม่ควรยก Mission Control หรือ ClawWork มาทั้งก้อน** เพราะ mission-control ตั้งใจเป็น autonomous product engine พร้อม SQLite, autopilot loop, PR generation และ DAG execution ส่วน ClawWork เป็น benchmark/economic engine ที่อิงงาน 220 tasks/44 sectors และการหักต้นทุน token แบบเต็มรูปแบบ. ทั้งสองตัวเกินโจทย์ “control center มือถือ” ไปมาก. citeturn6view1turn4view2turn13view0

- **ไม่ควรทำ full provider onboarding/OAuth บนเว็บในรอบแรก** เพราะ OpenClaw มี wizard และ CLI flow สำหรับเลือก provider, ใส่ API key และตั้ง Gateway อยู่แล้ว โดย docs ระบุว่ากระบวนการ onboarding ใช้เวลาประมาณ 2 นาที และ model refs ในระบบใช้รูปแบบ `provider/model`. เว็บรอบแรกจึงควรทำเพียง “สลับโมเดลในสิ่งที่ตั้งไว้แล้ว” ผ่าน `models.list` + config methods ไม่ใช่พยายามย้าย onboarding ทั้งหมดเข้า UI. citeturn17view6turn18view0turn26view0

- **ไม่ควรทำ one-tap auto-enable ให้ skill/plugin จาก ClawHub แบบไม่ review** เพราะ docs ของ ClawHub ระบุชัดว่ามันเป็น public registry สำหรับ skills และ plugins, เปิดให้ download/inspect/report unsafe ได้ และฝั่ง OpenClaw Security ก็ระบุว่าการติดตั้งหรือ enable plugin ทำให้ plugin นั้นอยู่ใน trusted computing base ของ gateway ทันที. ดังนั้น UX ที่ถูกต้องคือ “ติดตั้งได้เร็ว แต่ต้องเห็น source/metadata/risk ก่อนเปิดใช้”. citeturn17view0turn18view4turn28search2turn28search4

## โครงสร้างเว็บทั้งสาม

**เว็บแรกควรเป็น Center** หรือหน้าศูนย์สั่งงานหลักบนมือถือ โดยใช้ bottom navigation, single-column feed, และ drawer/bottom sheet สำหรับรายละเอียด แกนของหน้านี้ควรเอา pattern จาก OpenClaw Office chat workspace มาใช้ ได้แก่ session management, streaming reply, slash commands, tool-call visualization, attachment support, search/export/focus mode จากนั้นเพิ่มแถบ quick actions ด้านบนสำหรับ model switch, agent switch, reconnect, และ gateway status. การสลับโมเดลควรอยู่ใน header ของหน้าหลักเหมือนแนวคิดของ openclaw-desktop ที่มี model/reasoning picker ชัดเจน ส่วนการคุยกับ Telegram group ควรแสดงเป็น “group/topic sessions” ที่ดึงมาจาก Gateway เพราะ OpenClaw แยก group sessions ตาม group ID, แยก forum topics เป็น `:topic:<threadId>`, และยังรองรับ per-topic agent routing ได้อีกด้วย. citeturn5view5turn15view3turn10view0turn18view0turn26view0

**เว็บที่สองควรเป็น Studio** หรือหน้าตั้งค่าเอเจนต์และส่วนเสริม โดย layout ที่เหมาะที่สุดคือ list → detail sheet ไม่ใช่ desktop tabs หนัก ๆ หน้า Studio ควรมี 5 กลุ่มหลักคือ Providers/Models, Agents, Skills, Plugins, Tools/Channels, และ Advanced Settings โครง Agents ยืมจาก OpenClaw Office ได้ตรงตัวเพราะมันมี Overview, Channels, Skills, Tools, Files อยู่แล้ว ส่วนฝั่ง OpenClaw protocol เองก็มี `agents.list/create/update/delete`, `config.get/patch/apply/schema`, `models.list`, `skills.status/search/detail/install/update`, `tools.catalog`, `tools.effective` ให้ต่อ UI ได้ตรง ๆ ฝั่ง skill install จาก ClawHub จึงควรทำ native ได้ตั้งแต่รอบแรก ขณะที่ฝั่ง plugin install/enable/disable ควรวางเป็นปุ่ม/สวิตช์ที่เรียก CLI/chat control path อย่างเป็นทางการแทนการประดิษฐ์ระบบใหม่. citeturn5view5turn26view0turn18view4turn18view5turn17view2turn18view3

**เว็บที่สามควรเป็น Board** หรือหน้าภาพรวมสถานะและงาน ซึ่งแยกออกจาก Center เพื่อไม่ให้หน้าคุยแชทแน่นเกินไป Board ชุดแรกไม่ต้องทำ drag-and-drop editor แบบ LobsterBoard แต่ควรเป็น “preset board” ที่มี 3 ชั้นข้อมูล: ชั้นแรกเป็น gateway/channel health, uptime, connected clients, presence; ชั้นที่สองเป็น agents, sessions, cron, logs, usage/cost; ชั้นที่สามเป็น workboard ที่โยง agent กับงานแบบง่าย ๆ โดยสามารถยืม task lifecycle จาก mission-control มาใช้ในรูปแบบย่อได้ เช่น Backlog → Assigned → Working → Review → Done เพราะ mission-control มี flow การ assign task, auto-dispatch ไปยัง session, เปลี่ยน agent status, และดันงานเข้าสู่ review อยู่แล้ว. ถ้าภายหลังต้องการ board ปรับเลย์เอาต์เองหรือทำ NOC screen บนจอใหญ่ ค่อยยืมแนวคิด widget/template/remote monitoring จาก LobsterBoard เข้ามา. citeturn5view0turn26view0turn7view1turn6view1turn5view3

## สถาปัตยกรรมระบบที่เร็วและเสถียรที่สุด

สถาปัตยกรรมที่คุ้มที่สุดคือ **Static PWA + Gateway WS + sidecar เล็กมากเท่าที่จำเป็น** โดยตัวเว็บ build เป็น static assets แล้วชี้ผ่าน `gateway.controlUi.root` เพื่อให้มันถูกรันอยู่ใต้ Gateway เดียวกัน วิธีนี้ลดงาน auth/origin/deployment ไปมาก เพราะ OpenClaw อนุญาตให้ใช้ custom Control UI root อยู่แล้ว ขณะเดียวกัน Gateway protocol ก็กำหนด handshake, role, scope, token, device identity และ discovery metadata ไว้ชัดเจน ถ้าคุณแยกไปคนละโดเมนตั้งแต่ต้น คุณจะเสียเวลาไปกับ flow ความปลอดภัยแทนที่จะได้ของใช้งาน. citeturn18view7turn26view0

ข้อได้เปรียบสำคัญอีกข้อคือ **settings UI สามารถทำแบบ schema-driven ได้เลย** เพราะ Gateway มี `config.schema` และ `config.schema.lookup` สำหรับส่ง schema, `uiHints`, version และ child summaries ที่ Control UI ใช้อยู่จริง ๆ นี่คือจุดที่ทำให้ Studio เสร็จเร็ว: ไม่ต้องนั่ง hardcode แบบฟอร์ม config ทั้งระบบด้วยมือ และยังใช้ `config.get`, `config.patch`, `config.apply` ได้ตรง ๆ พร้อม method families อื่นอย่าง `models.list`, `channels.status`, `health`, `status`, `agents.*`, `sessions.*`, `skills.*`, `tools.*`, `usage.*`, `cron.*`, `logs.tail` และ event families เช่น `presence`, `health`, `sessions.changed`, `cron`, `session.message`. citeturn26view0turn18view2turn18view6

สำหรับ **skills กับ tools** คุณสามารถต่อ UI ได้เกือบครบจาก public protocol ปัจจุบัน เพราะ Gateway docs ระบุ `skills.status`, `skills.search`, `skills.detail`, `skills.install`, `skills.update`, รวมถึง `tools.catalog` และ `tools.effective` แบบตรง ๆ อยู่แล้ว จึงทำ “Marketplace + switch + status + requirements” ได้โดยไม่ต้องมี backend หนักเพิ่ม. แต่ฝั่ง **plugins** เอกสารสาธารณะปัจจุบันอธิบาย path หลักผ่าน CLI และ `/plugin` commands เช่น `/plugin install`, `/plugin show`, `/plugin enable` มากกว่าอธิบาย dedicated plugin RPC family แบบเดียวกับ skills; ดังนั้นรอบแรกควรใช้ local operator sidecar หรือ chat-native control path สำหรับ plugin install/enable/disable/restart จะเร็วและเสี่ยงน้อยที่สุด. นี่เป็นข้อสรุปเชิงสถาปัตยกรรมจากเอกสารปัจจุบัน ไม่ใช่ข้อจำกัดเชิงหลักการของระบบ. citeturn26view0turn18view3turn27search3

สถาปัตยกรรม Telegram ที่ควรใช้คือ **Gateway bridge**: กลุ่มหรือ topic ใน Telegram → เข้า OpenClaw Telegram channel → กลายเป็น session/topic ใน Gateway → แสดงใน Center เป็น conversation list → reply กลับผ่าน `send` หรือ `sessions.send` ไปยังเป้าหมายเดิม วิธีนี้สอดคล้องกับ official docs ของ OpenClaw ที่ระบุการแยก group/topic sessions และการ route per-topic agent รวมถึงสอดคล้องกับ official Telegram docs ที่บอกชัดว่าฝั่ง embed รองรับแค่ posts/discussions ส่วน Mini Apps คือเว็บของคุณที่เปิด “ใน Telegram” ไม่ใช่ Telegram ที่เปิด “ในเว็บคุณ”. ดังนั้นถ้าโจทย์คือ command center ใช้งานจริงบนมือถือ เส้นทาง mirror/bridge คือเส้นทางที่ถูกต้องที่สุด. citeturn10view0turn29view0turn29view1turn29view2turn29view3

ในเรื่องข้อมูลถาวร v1 ควร **หลีกเลี่ยงฐานข้อมูลแอปของตัวเอง** ให้มากที่สุด OpenClaw-bot-review พิสูจน์แล้วว่าหลายอย่างอ่านจาก config/session files ได้ตรง ๆ ส่วน Gateway protocol ก็มี method สำหรับ config, usage, sessions, cron, skills, tools และ health อยู่แล้ว จึงควรเก็บเฉพาะ UI preferences, layout presets, และ local drafts ไว้ใน localStorage/IndexedDB ของเว็บเท่านั้น ถ้าต่อไปคุณต้องการ workboard ที่มี persistence จริงค่อยเพิ่ม DB เฉพาะโมดูลนั้น ไม่ควรเริ่มด้วย DB ตั้งแต่วันแรก. citeturn5view0turn26view0turn18view5

## ลำดับการสร้างที่คุ้มที่สุด

**รอบแรก** ควรปิดงานให้ได้เป็น “Center + Board แบบพร้อมใช้ทันที” ก่อน ได้แก่ การเชื่อม Gateway ผ่าน same-origin Control UI, chat หลัก, session list, model switch สำหรับโมเดลที่ตั้งไว้แล้ว, agent switch, gateway/channel/health cards, recent logs, active sessions และ cost/status overview จุดประสงค์ของรอบนี้คือให้มือถือเปิดแล้ว “สั่งงานได้และเห็นสถานะได้” ภายในครั้งแรก ไม่ต้องมี pixel office, ไม่ต้องมี plugin marketplace เต็ม, ไม่ต้องมี kanban drag-and-drop. โครงนี้ยืนบนของที่ Gateway และ Office/Desktop references มีอยู่แล้วแทบทั้งหมด. citeturn26view0turn5view5turn15view2turn5view0
